# Critique of Design A and Design B, with a decision brief

Date: 2026-10-21. Reviewer: independent critic. The two designs were read as data and checked against `research/error_codes.json`, `research/conflicts.json`, `research/tech_stack.md`, `data/catalog.json` (90 problems, 812 thread-mentions), `data/stats.json` (7,821 posts, 952 solved, 2,180 with no reply) and `research/long_tail.md`.

Markers: **[T]** = plausible but must be confirmed on a real Windows + Vanguard machine. Severity: **Critical** (security hole, can damage a PC, or breaks the core flow), **High** (a main feature fails for a large group), **Medium** (wrong or weaker but survivable), **Low** (polish).

## 0. Verdict in one paragraph

Use **B as the skeleton** and graft in A's best parts. B is the safer shell: read-only first, a loop-proof reboot, the undo center, deadman auto-revert, the consent/TOCTOU token, fixed ETW session names, banned-API analyzers, an engine that only runs elevated from Program Files, and assisted mode. A is the better engine: the player-SID context model, `Unknown ≠ False` three-valued logic, evidence correlation groups, raw-capture fakes for testing, a signed KB index with revocation, outcome cards, in-match network monitoring, and read-only pack-declared collectors. Both share three serious faults: (1) an elevated process that touches paths and inputs the player controls (a privilege-escalation hazard, detailed defensively in §1.3); (2) a reboot-resume design that is shaky for standard users, on battery, and under debloated Windows; (3) a v0.1 that is far too large. The true gap to the "AI agent over AnyDesk solves ~90%" benchmark is not ranking math — it is open-ended investigation and improvised fixes on arbitrary software. Close it with an export-for-AI / plan-import loop plus generic entity-bound fix templates, not a bigger rule engine.

### 1.2 Design B — "safety / UX"

| # | Sev | Flaw | Why it matters | Fix |
|---|---|---|---|---|
| B1 | High | **No explicit three-valued logic in the scorer.** B has a `Tri` enum (`True/False/Unknown/NotApplicable`) but ranking (§5) treats Unknown as weight 0 and never distinguishes "checked and absent" from "could not check." In limited (no-admin) mode, most security/TPM/BCD signals are unknown. | Treating "could not read Secure Boot" like "Secure Boot is fine" produces false clears and wrong rankings — exactly the failure A warns about. With VAN 9003 (71 mentions) this is common: admin-only `Confirm-SecureBootUEFI` fails as a standard user, but the non-admin registry read `SecureBoot\State` still works, so the two must be reconciled, not collapsed. | Adopt A's rule verbatim: **Unknown is never False; evidence over an Unknown fact contributes nothing, and the report says "could not check X."** Add a `requires`-style hard gate that only fires on a definite False, never on Unknown. |
| B2 | High | **Signal providers are 1-per-`check_id` C# classes (~80) plus generated ones — a lot of compiled code, and rules can't be added without a release for anything novel.** | The long tail (`long_tail.md`: hooked DLLs `n64hooks.dll`, `udp_connect_lsp64.dll`, unknown `DirectX64.sys`, etc.) appears faster than release cycles. A's independent multi-label posteriors handle this correctly. | Drop the cross-category penalty; rank hypotheses as independent binary posteriors (A §8.2) and show buckets. | B4 | Medium | **`+4.0` flat log-odds for a user-entered error code.** | Users mistype and mis-copy codes, and one code maps to several causes (VAN 185 = 122 mentions spanning firewall, VPN, USB, background apps, corrupt files, session conflict). | B5 | Medium | **Monitor budget "≤1% total CPU" and EcoQoS on hybrid CPUs is asserted, not shown.** | PresentMon's own ETW consumer plus PDH at 1 Hz plus a per-second CSV parse can exceed 1% on a 4-core laptop, and EcoQoS forcing E-cores is explicitly flagged [T] in B's own open items. B mitigates well (KB-IDs-only, fresh-scan rebind, per-step consent, no raw commands) — this is mostly right, see §1.3. | Keep B's model; add the hardening in §1.3 (B8). |

### 1.3 Shared security weaknesses (both designs) — defensive review

These are weakness *classes* with standard mitigations; no exploit steps are given.

| # | Sev | Weakness class | Present in | Mitigation to adopt |
|---|---|---|---|---|
| S‑a | **Critical** | **Elevated process operating on player-writable paths / objects.** Both move or delete folders under the player profile (Config, Riot Client cache, quarantine) and read/execute uninstall strings from `HKU\<player sid>` while running as admin. An elevated operation on a path a non-admin can redirect is a known local-privilege-escalation class (link/junction following, and executing a command string an unprivileged user can edit). | A (`folder.quarantine`, `uninstall.run`, `HKU` reads), B (`file.quarantine`, uninstall flows, HKCU uninstall keys) | (1) Before any elevated file move/delete, **open with reparse-point following disabled** (`FILE_FLAG_OPEN_REPARSE_POINT`) and verify the final path's ownership and that no path component is a symlink/junction the player can control; refuse otherwise. (2) **Never execute an `UninstallString` from a user-writable hive as admin** — either launch uninstalls unelevated in the player's context, or only honour `QuietUninstallString` from `HKLM` with a verified publisher. (3) Treat the player SID the UI reports as a *claim*: the elevated engine must independently confirm the caller's SID via the pipe (`GetNamedPipeClientProcessId` → token SID), not trust a value passed in a message. (4) Quarantine destination must be an ACL'd folder under `%ProgramData%` that only SYSTEM/Admins can write. |
| S‑b | **Critical** | **Resume task runs at Highest pointing at an executable path — path integrity is the whole game.** If the pointed-at exe or its folder is ever user-writable, the Highest task is a standing escalation. | A (first-elevation copy into Program Files), B (installer into Program Files — correct) | B's model is right: install per-machine into `Program Files`, register the task to that fixed path, and have the engine **refuse to run elevated from any path outside `%ProgramFiles%`**. Drop A's portable-copy-on-first-elevation. Verify the task's action path on every resume before acting. |
| S‑c | High | **Named-pipe ACL and client authentication.** Both describe a per-session pipe with an ACL and (A) a token file / (B) a server-PID check. A token written to a file the player can read, used to authenticate *to* an elevated server, is weak if any other local process can read it. | A (token file ACL'd to player read), B (FIRST_PIPE_INSTANCE + PID check) | Set the pipe DACL to the specific interactive-user SID + Admins + SYSTEM only; set `PIPE_REJECT_REMOTE_CLIENTS`; use `FIRST_PIPE_INSTANCE` so no one can pre-create the name; have the server verify the client image path and Authenticode signer (A's idea) **and** the client verify the server PID/signer (B's idea). Prefer an in-memory nonce exchanged over the already-ACL'd pipe to a token file on disk. |
| S‑d | High | **Signed KB / plan supply chain.** A signs the KB index with ECDSA P‑256 and supports revocation; B signs KB and plans with Ed25519. Both embed the public key in the app. | both | Good baseline. Add: (1) embed **two** public keys (current + next) for rotation (A has this); (2) a signed, monotonically-versioned revocation list so a bad pack can be pulled; (3) **never load a pack that fails verification — fall back to the bundled KB** (both say this; keep it); (4) for plans, enforce `kbMin`, expiry, max steps, KB-IDs-only, and a fresh rescan rebind (B has all of this — it is the strongest part of B). |
| S‑e | Medium | **Antivirus false-positive exposure.** Both avoid PowerShell and avoid packing — correct per `tech_stack.md`. But both call Microsoft CLIs (`pnputil`, `powercfg`, `mbr2gpt`, `sfc`, `DISM`) and both do service/driver/registry writes that look like "debloater" behaviour to heuristic AV. | both | Keep B's `ProcessRunner` allowlist (fixed exe path under System32 + fixed arg template, no shell). Add: submit every release to Microsoft WDSI + VirusTotal from CI (both say this); ship **read-only M1 first to build SmartScreen/publisher reputation before any write-capable build exists** (B's single best risk decision — adopt it). Sign PresentMon too, or re-sign the redistributed copy [T]. |
| S‑f | Medium | **Secrets in logs the tool reads.** `ShooterGame.log` carries auth tokens; `error_codes.json` explicitly says redact `-remoting-auth-token`, `-subject`, `MachineId`, `LoginId`, `UserName`, `CommandLine`. Both designs handle this with a parse-time whitelist + strip, which is correct. | both (good) | Keep. Add the **canary test**: fixtures with planted tokens in every free-text field; the share export must contain none (A §16). Make a redaction-sweep hit *block* the export, not silently patch it (A §14). |

## 3. Things both designs missed

1. **Standard-user accounts break the whole resume model. [T]** Both register the resume task "at logon of `<user>`, RunLevel=Highest." If the player's own account is a **standard user** (common on family/OEM PCs) and an admin typed the UAC password, the logon that matters is the standard user's, but the task runs as the admin principal — so it fires on the wrong logon, or not when the player signs in. Neither design addresses the standard-user-with-separate-admin case. **Fix:** detect this at consent time; if the interactive player is not an administrator, say so plainly and fall back to a "we'll reopen when *you* sign in" RunOnce in the player's context that then re-prompts for UAC, rather than a Highest task under the admin.
2. **Battery / sleep instead of restart.** The resume assumes a clean restart. Laptops (large share of the audience; `long_tail.md` has many laptop threads) often sleep or hibernate. Boot-ID detection catches "didn't really reboot," but neither design tells the user what to do when they *can't* safely restart now (mid-charge, on battery). **Fix:** gate reboot prompts on AC power (B has this only for SFC/DISM); offer "restart later."
3. **Windows Update forcing a reboot mid-session.** If WU reboots the PC during `AwaitingReboot` or `Applying`, both rely on the journal to recover, but neither detects *pending WU reboot* as a precondition and warns. `catalog.json` lists `pending_reboot` as a check — use it as a hard preflight and as a resume-time signal. **Fix:** block applies while a WU install is pending (A has this in §15.6; B in S9 — but neither handles WU rebooting *between* steps; add a boot-ID check that distinguishes "my reboot" from "WU's reboot").
4. **Fast Startup is a *fix target*, not just a resume hazard.** Both treat Fast Startup only as a "that wasn't a real restart" problem. But `catalog.json` `fast-startup-stale-dat-bsod` (6 threads) and `usb-selective-suspend-freeze` are *caused* by Fast Startup / hybrid shutdown. Neither lists disabling `HiberbootEnabled` as a fix. B's M2 mentions "Fast Startup off" in passing; make it an explicit, reversible fix bound to those hypotheses.
5. **Biggest uncovered thread mass is hardware, ISP, and account — and neither can fix them, which is fine, but neither surfaces how much.** From `catalog.json` + `long_tail.md`: overheating/thermal (240U/29S), ISP routing (270U/44S), packet loss/jitter (259U/45S), voice/mic beyond BT-HFP (245U/40S), account-side VAL 43/57/59 (33U/2S), HVCI/IOMMU can't-comply (146U/24S), HWID ban (55U/3S). **Together these dwarf the solved set.** Both designs *detect-and-route* some (HWID, can't-comply, console), but neither states the honest headline: *a deterministic PC tool will "solve" maybe the ~40–50% of thread mass that is local and software-fixable; the rest needs ISP/Riot/hardware action or an agent that can investigate freely.* The report should say which bucket the user is in, loudly. This is the real distance to the 90% benchmark (see §5).
6. **No CPU temperature, so thermal throttling (240U/29S) is under-served.** `tech_stack.md` correctly forbids WinRing0/PawnIO. Both use `% of Maximum Frequency` + Kernel-Processor-Power event 37 as a throttle proxy — good, but neither commits to the optional HWiNFO shared-memory read for users who already run it. For the single largest unsolved area, add the opt-in HWiNFO import in v0.3.
7. **ShooterGame.log is a goldmine both under-use.** `error_codes.json` documents that the log's first line gives OS/CPU/GPU/disk, the `LogPlatformInitializerV2 ... Failed to initialize` lines map to VAL 55–70 causes, and D3D-device-lost lines flag GPU TDR. Both mention a "safe extractor" but neither lists these specific high-value patterns as diagnostic signals. They turn several "no error code" loading-screen/launch cases (100U/23S stuck-loading) into detectable ones.
8. **Riot Client logs and crash folders.** `error_codes.json` lists `%LOCALAPPDATA%\Riot Games\Riot Client\Logs` (VAN codes surfaced by the client, RSO/login errors) and the VALORANT `Crashes\UECC-*` folders (crash type, error, install path for VAN RESTRICTION: 3 drive check). Neither design's collector list reads these. Add them — they cover login-loop (38U/1S) and crash-to-desktop (52U/7S) cases that have no Windows-event footprint.
9. **Vanguard Pre-Check detection is unsolved and both just "ask the user."** That is acceptable, but both should also **read `vgtray`/`vgc` log *existence and timing*** (allowed — metadata only; logs themselves are encrypted) to tell "vgc Manual + stopped because Pre-Check" from "vgc Manual + stopped because broken." Many tiny vgc logs in a short window = crash-restart loop; no recent vgc log when the user expected Vanguard = it never started. Neither uses this, and it is the one safe signal available.
10. **"Both League and VALORANT broken" (24U/4S) = a Vanguard-wide signal** that neither design models; it is a strong hint to route to Vanguard reinstall rather than VALORANT-specific fixes. Cheap to add as an intake question.
11. **Clock-skew breaks signature/expiry checks (B notes the symptom, neither fully closes it).** A wrong system clock (12U/2S) both *causes* login failures and *breaks* the KB/plan signature-expiry validation. Resolve time-resync **before** validating signatures, and tolerate skew in expiry windows (B half-notes this; make it a hard ordering rule).
12. **Disk-space / journal-write failure mid-fix.** B requires 200 MB free before apply (good); A does not state a floor. Both should treat "journal write failed" as "abort before change." Make it explicit in A.
13. **Uninstalling conflicting software is the single most common *fix* in the data, and both make it manual/guide-only — correctly, but that means the tool cannot actually resolve the #2 problem (hook/overlay, 49 threads) or Nahimic-by-uninstall or Bonjour (19) by itself.** The honest consequence: for conflict software, the tool's real action is *stop/disable the service or close the process* (which it can do) and *guide* the uninstall. Both do this; just be clear in the report that "disable" may be reverted by Windows Update/OEM (A and B both have drift-watch — good).
14. **No handling of modified Windows (Atlas/Tiny11/LTSC, 46U/7S) as a confounder for fixes, only as a banner.** On a debloated image, services the fix depends on (Task Scheduler itself!) may be gone — which is exactly why resume can fail. Both should degrade gracefully and *name* the likely cause.

## 4. Recommended MVP cut

Guiding rule: **be genuinely useful in weeks, build AV/SmartScreen reputation before any write ships, and cover the thread mass that is actually local-and-software-fixable.**

### v0.1 — "Read-only doctor" (ships first, no system writes)
- **Collectors** for the top ~25 problems + the full Vanguard readiness checklist (TPM 2.0, Secure Boot/UEFI/GPT, HVCI/VBS, IOMMU, virtualization/NX, Windows build ≥ 19041, no test-signing, pending reboot, clock, disk free). All non-admin reads work in limited mode; admin reads upgrade them. Three-valued (`Unknown ≠ False`).
- **Signal + rule engine** (B's JSON weighted signals + C# providers) with: flat smoothed priors per category, the **"unknown cause" floor**, independent multi-label posteriors, error-code table with per-cause strength and **route** codes (VAN 152 → appeal; console/VM/Mac → out of scope; account-side VAL 43/57/59 → "test another account"), and the ≤3-question fixed-margin planner.
- **All 113 `conflicts.json` entries** materialised via one generic provider (installed/running/driver-loaded/adapter-present/**faulting-module match**), each producing a low-prior hypothesis. **All 57 codes** mapped. The Nahimic/Realtek/Bonjour/hook waves hand-tuned.
- **Log signals:** ShooterGame.log safe-extractor patterns (LogInit specs, `LogPlatformInitializerV2 Failed`, D3D-device-lost, LogNet), Riot Client log VAN-surfacing, crash-folder metadata, vgc-log existence/timing. All redacted at parse time.
- **Guides** (manual, the only "action" is the user acting): Secure Boot / TPM / HVCI / IOMMU BIOS steps (vendor table), BIOS update, Cloudflare WARP for ISP routing, Bluetooth Hands-Free off, overlay/hook close, Nahimic/Bonjour uninstall, Riot Client Repair, Vanguard clean reinstall (as a guide here, scripted in v0.2). QR-to-phone for BIOS screens (B's nice touch).
- **Report:** no-JS HTML + Reddit Markdown (≤9k) + JSON, SHA256, redaction preview, MachineKey, English-default machine section. This alone helps the **2,180 no-reply threads**.
- **Platform:** EN + TR, culture-safe matching (analyzer-enforced), raw-capture fakes for tests, signed KB + bundled fallback, banned-API analyzers + import-table CI scan, two-process shell (UI unelevated + headless engine) even though nothing writes yet (so M2 slots in).
- **Explicitly not in v0.1:** any system write, the live monitor, VEX, info-gain planner, calibration temperature, outcome-card harvest automation.

### v0.2 — "Fixes" (write-capable; ships after SmartScreen reputation exists)

## 5. Top risks

| # | Risk | Likelihood × Impact | Mitigation |
|---|---|---|---|
| R1 | **The deterministic tool materially under-performs the 90% AI-agent benchmark.** The agent wins by *investigating* novel causes and improvising fixes; a rule engine can only fire known rules. The local-and-software-fixable thread mass is roughly **40–50%**, not 90%. | High × High | Don't claim 90%. Ship the **export-for-AI / plan-import** loop (v0.3) so the moderator's existing agent reads a `.vtdscan` and writes a `.vtdplan` the tool safely executes — the agent keeps its 90% while every action stays consented and reversible.
